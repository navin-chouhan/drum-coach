## Major

**M1 · audio / lesson / practice · A route change mid-take doesn't end the take, and its clicks go silent for
2–4 s.** Verified (traced); which notification iOS posts for a given plug/unplug is suspected.
`modules/drum-audio/ios/AudioEngineHost.swift:801-822` (`handleRouteChange`): when the output changes without a format
change (e.g. headphones ↔ speaker, the hub's 3.5 mm unplugged), native calls `cancelLocked(fromMs: nil)` (every queued
click, count word and app-played note is dropped) and emits only `onRoute`. No take listens to `onRouteChange`: the
lesson (`features/lesson/useLesson.ts:108-109`), Practice (`features/practice/engine.ts:62-63`) and Songs
(`features/songs/interrupt.ts:16-17`) stop only on `onInterruption` `began`/`engine-stopped` or AppState. So the take
runs on: core's feeder already counts those events as handed over (`packages/core/src/play/feeder.ts:28-30`,
`plannedTo` up to 4 s ahead) and won't plan them again, so there's no click until `plannedTo` falls inside the next
2 s window; the take keeps scoring with the old route's `latencyMs` (captured once, `take.ts:359`) while
`useLatencyRouteSync` switches `settings.latencyMs` to the new route; the take is saved as a normal run and counts for
the ladder / Climb. AUDIO-DESIGN §3.3 and the §4 table say "A running take ends as interrupted … the new route's
latency isn't the one it was scored against". Only a format change (`handleConfigChange`, line 825) emits
`engine-stopped` and is handled.
Repro (device): start a 16-bar lesson take on the hub route, pull the 3.5 mm jack at bar 4 → the click stops for a few
seconds then comes back on the speaker; the take finishes and is saved and judged normally.
Fix: in `handleRouteChange`, when `changed && wasRunning`, also emit
`emitInterruption?(["type": "engine-stopped", "at": now, "cause": "route-change"])` (the TS side then stops every
take through the existing listeners, keeps ≥ 2 whole bars flagged). Or, TS only: in `watchInterruptions`, `useLesson`
and `practiceEngine.start`, subscribe `audio.onRouteChange(() => interrupt())`. Add a Vitest case in
`features/songs/interrupt.test.ts` and the engine tests.

**M2 · audio · Touch pads are silent until a take starts (on every launch, and again after the app was in the
background).** Verified (traced).
`AudioEngineHost.swift:503-506`: `playNow` returns NaN ("playNow() before start()") while the engine isn't running.
Nothing starts the engine when a play screen with touch pads mounts: `audio.start()` is called only by a take
(`take.ts:264`), Setup's Kit test (`setup/SetupScreen.tsx:241`), the latency panel, the sound panel, the metronome and
the song screen (`songs/SongScreen.tsx:60`). The lesson player (`lesson/LessonScreen.tsx:211`), the placement test
(`lesson/PlacementScreen.tsx:108`) and Practice's play screen (`practice/PlayScreen.tsx:257`) pass
`playNow={audio.playNow}` but never start the engine. And `enterBackground` (`AudioEngineHost.swift:734-745`) stops it
again, so after Home and back the pads are silent until the next Play. AUDIO-DESIGN §3.4: "`start()` is called when a
play screen mounts". The hits themselves still reach the hit bus (the pads light, takes score), so it shows up as
"the touch pads make no sound" before the first Play: the FINAL-CHECKLIST §7 "Unplug the kit: the player switches to
the touch pads" step, and the simulator flow.
Repro: launch the app (not the first run) → Journey → Start → (no kit) tap the snare touch pad: no sound. Press Play:
the count-in and the pads sound. Home, back: silent again.
Fix: a small `useAudioEngine()` hook in `src/platform` (or `src/play`) that calls `void audio.start().catch(() => {})`
on mount and on `AppState` → `active`, used by `TouchPads` (or the three screens). It's idempotent (a no-op while
running).

**M3 · practice · The metronome reacts to kit gestures while you play along: a tom fill changes the tempo, a double
crash or quick pedal stops it.** Verified (traced).
`features/practice/MetronomeScreen.tsx:66`: `useKitMoves({ yes: toggle, faster, slower })` with no `playing`
option, so `padCommands` treats every hit as "between takes" (`packages/core/src/engine/padCommands.ts:14-21`): two
tom-1 hits < 400 ms apart = faster (+5 BPM and the click restarts, line 43), two floor-tom hits = slower, two crashes or
three pedal chicks < 400 ms apart (quarter-note chicks at ≥ 150 BPM, 8ths at ≥ 75) = Start/Stop. Every tom fill has
such doubles. The metronome is the one screen where you play without a take (the web has no such screen; elsewhere a
running take passes `playing` and only crash × 4 counts).
Repro: Metronome at 100 BPM → Start → play a fill with two 16ths on tom 1 → the tempo jumps to 105 and the click
restarts.
Fix: `useKitMoves(…, { playing: running })`, and map `stop` to `stop()` so crash × 4 stops it (the screen's line says
"Start / Stop (hi-hat pedal × 3)": keep that only while stopped). Update the header comment and the checklist line.

**M4 · checklist · After §4 M8 the kit stays disconnected for the rest of the session.** Verified (traced).
`modules/drum-midi/ios/MidiInputHub.swift:107-121,249-269` connects exactly one source, and a connected source becomes
the selection (`selectedID`/`selectedName`, lines 264-265). FINAL-CHECKLIST §4 M8 has the owner **Select** the Network
MIDI session on `/dev/midi` (`app/dev/midi.tsx:118`), which disconnects the e-Drum; nothing in the checklist selects
the kit again, and with a selection set the `e-Drum` auto-select doesn't run (`InputSelection.swift:28-32`). The dev
screen's select isn't saved to `drumcoach.midiInput`, so only a relaunch or a manual pick restores it. Sections 5-7
(audio checks with the kit, every screen, kit gestures) would then run with the kit pill grey and no hits.
Fix (docs): at the end of M8 add "Switch **Network MIDI session** off, then **Select** e-Drum under Devices (or Setup →
MIDI input → Use this) and check the sidebar's kit pill is green." Optionally (code): when the selected source goes
offline (the session switched off), fall back to auto-select: in `select(id:)`/`reconcileLocked`, keep `autoSelect`
true for an explicit select so a dead selection falls back to the preferred names.

## Minor

**m1 · audio · The metronome keeps showing "running" but is silent after Home / lock / a call.** Verified (traced).
`MetronomeScreen.tsx:21-63` never listens to `audio.onInterruption` or AppState. `enterBackground`
(`AudioEngineHost.swift:734-745`) stops the engine, and `schedule` drops everything while it isn't running
(`AudioEngineHost.swift:415-421`), but the screen's `running` stays true and the beat dots keep moving. Fix: stop on
`began` / `engine-stopped` and on AppState ≠ active (the `useInterruptions` hook in `features/songs/useInterruptions.ts`
does exactly this: move it to `src/platform` and reuse it).

**m2 · progress · The show-off trophy can't be earned and there's no show-off set, though Songs shipped.** Verified.
`features/progress/progress.ts:93` calls `badgeProgress(runs, progress, checkpoints, now)` without the ready songs and
`bestSongBars`; the web passes `showoff.map(x => x.id), bestSongBars` (`src/ui/ProgressView.tsx:64-66`) and lists the
show-off set (`ProgressView.tsx:151-153`). So "Show-off song" always reads 0 / 16 bars. The header comment
(`progress.ts:4`, "Songs come after v1") is out of date. Fix: read `storage.songs.list()` in `useStoredData`, compute
`songVerified`/`songReady`/`songBarCount` as the web does (core `engine/youtube.ts`/`stageSong.ts`), pass them, and add
the set's card with "▶ Play it" → `songHref`.

**m3 · setup · Kit test still says the hardware keyboard needs a later build.** Verified.
`features/setup/SetupScreen.tsx:251`: `KEYS_LINE.replace('No kit? Keys:', 'No kit? Tap a drum. A hardware keyboard needs
a later build:')`. drum-keys is merged and mounted app-wide (`app/_layout.tsx:16`). Fix: show `KEYS_LINE` as is (or
"No kit? Tap a drum, or use a hardware keyboard: …"). W1 touches setup for calibration keys; whoever lands second.

**m4 · latency · A never-measured output scores with the previous output's number.** Verified (traced).
`features/latency/latencyByRoute.ts:42-47` (`syncToRoute`): an unknown route only clears `latencyChecked` and keeps
`latencyMs`. A take on Bluetooth (150–250 ms) is then scored with the hub's ~10–30 ms, so every note reads "late".
AUDIO-DESIGN §3.3: "disables scored takes until it's measured, or the user chooses 'use the speaker's value'". Setup
shows "Not measured", but the lesson and Practice play on. Fix: when `!latencyChecked`, the lesson's and Practice's
main move shows the "measure latency (30 s)" notice first (the lesson already has `latencyHint` / `openLatency`), with
"use this value anyway".

**m5 · audio · The engine is never suspended.** Verified. Nothing calls `audio.suspend()` (only the wrapper,
`platform/audioCore.ts:164`). AUDIO-DESIGN §3.4: suspend after 60 s with no take and no touch-pad screen; a running
engine renders silence continuously (battery during a 2½-hour session). Fix: one idle timer in the app (reset by
`take.start`, touch-pad screens, the metronome), with M2's hook restarting it.

**m6 · lesson / practice · Audio interruptions end the take at JS-receipt time, not at the time native reports.**
Verified. `useLesson.ts:108` and `practice/engine.ts:62` call `stop('interrupted')` without `e.at`; Songs passes it
(`songs/interrupt.ts:16`, `songTake.ts:87`). If the JS thread is busy when `began` arrives, bars after the call began
are counted as played (with misses). Fix: pass `e.at` through `ctl.interrupt(at)` / `interrupt(at)` to
`take.stop('interrupted', at)`.

**m7 · setup · Setup re-reads storage on every hit.** Verified. `SetupScreen.tsx:44` `useLastHit()` re-renders the
whole screen per hit, and the render calls `readLatencyByRoute(kv())` (a SQLite read and JSON parse, line 52),
`setupChecks`, `latencyRow`, `otherRoutes`. During Kit test or "hit each pad" that's one storage read per stroke (the QA
m1 kind of cost). Fix: move `useLastHit` into the small `hit` view (a `LastHit` child component) and memo `byRoute` on
the settings version.

**m8 · e2e · `lesson-to-progress.yaml` can't leave the "lesson no longer exists" card.** Verified. The flow waits for
`lesson-back|lesson-missing` and then taps `lesson-back`, but the missing card's button has no testID
(`features/lesson/LessonRoute.tsx:19`). Fix: `testID="lesson-back"` on that button (it does the same thing).

**m9 · native (Swift) · drum-keys debug counters are read off the main thread; the editing count can stick.**
`modules/drum-keys/ios/KeyCatcher.swift:51-52,107` (`keysSent`, `focusCalls`, `focused`) are written on main and read
from the JS thread in `getDebugInfo` (`DrumKeysModule.swift:170-176`): a data race (harmless values, but TSan flags
it). Verified. And `editing` (line 49) only goes down on `textDidEndEditing`; if a focused field is torn down without
that notification (a Modal closing with the keyboard up), it stays > 0 and `focus()` never takes the keys back, so
the keyboard pads stop until relaunch. Suspected. Fix: read the counters with `DispatchQueue.main.sync` (or an atomic /
lock), and in `focus()` also accept `editing > 0` when no `UIResponder` in the key window `isFirstResponder` (or reset
`editing` on `UIWindow.didBecomeKeyNotification` and `refocus()` from JS).
