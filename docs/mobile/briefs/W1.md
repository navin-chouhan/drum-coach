# Brief: W1, app-wide keys (hardware keyboard commands)

## Goal
The `drum-keys` module (`apps/mobile/modules/drum-keys/**`) sends pad keys (CLAUDE.md keys) into the hit bus but passes
only Esc and Enter as commands. Make every web keyboard command work on an iPad hardware keyboard.

1. Inventory the web's command keys: `grep -rn "e.key ===" src` (e.g. `src/lesson/LessonPlayer.tsx` h = hints, b = band,
   c = check yourself; arrows and Enter in `src/play/IntroSlides.tsx`; ArrowLeft/Escape in `src/ui/Calibrate.tsx`;
   Escape closes sheets). Note which matter on the iPad (camera "c" self-check: only if the iPad app has it).
2. Extend drum-keys (Swift `KeyCatcher.swift`/`KeyPress.swift` + TS types + `contract.test.ts` + the Swift tests) to
   deliver the needed command keys (letters that aren't pad keys, arrows, Enter, Esc, Space only as a pad key).
   Keep pad keys exactly as now; a command key must never become a hit. Keep the mach host-clock timestamps.
3. Wire them where the iPad app has the matching feature: lesson (hints/band toggles), intro slides, calibration,
   sheets/modals (Esc). Prefer one small hook (e.g. `src/platform/useCommandKeys.ts`) over per-screen listeners.
4. If hidden-TextInput keyboard fallbacks still exist (lesson, songs), replace them with drum-keys, as long as the
   module covers them; otherwise report why not.

## Owns
`apps/mobile/modules/drum-keys/**`, `apps/mobile/src/platform/*keys*` (new hook), and the minimal keyboard-wiring edits
in `features/lesson/**`, `features/setup/**` (calibration), intro slides and sheets. Don't change lesson logic.
The Swift can't be compiled here: keep it simple, mirror existing style, and add Swift unit tests the cloud iOS build
runs (`DrumKeys.podspec` test spec).
