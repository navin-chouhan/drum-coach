# Brief: S1, MIDI spike (Gate 0)

## Goal
Prepare everything needed to prove or disprove, with numbers, that the Millenium MPS-150 delivers correct,
well-timed MIDI into an **Expo development build** on a real iPad, then an iPhone. Then the owner can run Gate 0 on
the MacBook in one sitting and paste the numbers back.

**Environment limits for this run.** You are in a Linux cloud container. There is no Xcode, no Swift toolchain, no
iOS simulator, no iPad and no kit. You write the code and check everything that *can* be checked here: TypeScript,
the JS tests, `expo prebuild`, config plugins and package versions. You state plainly what is unverified, mainly
that the Swift has not been compiled. Never claim a device result.

## Steps
1. **Search first.** Look for existing Expo or React Native CoreMIDI modules on npm and GitHub. Possible
   leads: `@motiz88/react-native-midi` (Web MIDI on the Expo Modules API), `react-native-midi`, and any `expo-midi`.
   Judge each on: works with the Expo Modules API and the New Architecture; maintained (last release, open
   issues); gives raw bytes; gives host timestamps (not JS receive time); supports hot-plug; licence. Record a table in
   GATE0.md. If one fully qualifies, say so and still recommend whether to adopt or vendor it. Default if none
   qualifies: our own small local module.
2. **Versions.** Check the current stable Expo SDK (npm `expo` `latest` reports 58.0.19, so verify), and the
   matching `expo-dev-client`, `react-native` and `react-native-audio-api` versions. Use
   `npx create-expo-app@latest` or an equivalent minimal template. Pin the versions. Record them in GATE0.md.
3. **Create `spikes/midi-probe/`.** A minimal standalone Expo app (its own `package.json` and lockfile; not a root
   workspace yet) with `expo-dev-client` and a local Expo module at `spikes/midi-probe/modules/drum-midi/` (Expo
   Modules API, Swift, iOS only; the TS side must fail gracefully on Android/web). Its own `.gitignore` covers
   `node_modules`, `ios`, `android`, `.expo`. The module exposes:
   - `listInputs(): { id, name, manufacturer, online }[]`, `select(id | null)`;
   - events `onInputsChanged` and `onMidi({ bytes: number[], hostTimeMs, nativeReceivedMs })`;
   - `nowMs()`: the one monotonic ms clock (mach host time → ms via `mach_timebase_info`), the same base as
     `hostTimeMs`;
   - `setNetworkSessionEnabled(bool)`: enables `MIDINetworkSession.default()` (connection policy anyone) so a Mac can
     send to the iPad over Network MIDI (M8).

   **CoreMIDI notes.** Use `MIDIClientCreateWithBlock` with a notify block for hot-plug (object added/removed, setup
   changed → re-list, and reconnect the selected source by name). For input, choose between
   `MIDIInputPortCreateWithProtocol(._1_0)` (UMP words: unpack each to its 1–3 MIDI 1.0 bytes, a fixed unpack and
   not a parser) and the legacy packet-list block (raw bytes), and justify the choice in GATE0.md. A packet timestamp
   of 0 means "now": use `mach_absolute_time()` then. Connecting must be idempotent, so no doubled hits after
   background/foreground (M4).
   **Native code only forwards bytes and a timestamp.** Note/velocity semantics, channel and filtering stay in TS. If
   a CoreMIDI packet can hold several messages (realtime bytes interleaved, running status), the *framing* (splitting
   a byte run into messages) lives in **TypeScript** with unit tests that run in this container
   (`spikes/midi-probe/src/shared/`). A1/A3 will move it into `@drum-coach/core` later.
4. **The shared parser.** Copy `src/engine/midi.ts` (and only the store-free parts of the `hits.ts` filters you need)
   into `spikes/midi-probe/src/shared/`. Put a header comment naming the source file and saying "copied for Gate 0;
   moves to @drum-coach/core in A1". Don't change the semantics.
5. **The probe screen** (one screen is fine; Expo Router is optional here):
   - the device list, with select, and an online/offline status that updates on hot-plug;
   - a live log of the last 50 messages: raw hex, status, channel, note, velocity, pad name per the KIT.md map;
   - counters for clock (0xF8), active sensing (0xFE), poly aftertouch (choke), note-off/velocity-0, and hits. They
     are counted in JS after the bytes arrive, so we prove the filtering happens in the shared TS path;
   - bridge delay `jsReceivedMs − hostTimeMs` (JS receive time read from `nowMs()` in the event handler): min,
     median, p95 and max, with reset;
   - a **tap-to-click test**: a 120 BPM click, 32 taps on the snare. Show mean offset and spread computed exactly
     like the web latency calibration (reuse or copy its math, with the source noted). The click must be scheduled
     **on the same clock** as the hit timestamps. Use `react-native-audio-api` if it can map its `currentTime` to host
     time (check its API, e.g. an output-timestamp or similar, and document the mapping). If it can't, add a native
     `scheduleClicks(startHostTimeMs, bpm, count)` in the module (AVAudioEngine + `AVAudioPlayerNode.scheduleBuffer(at:
     AVAudioTime(hostTime:))`) and use that; record which path was used and why. Also show the output latency the
     audio session reports, and use it in the offset the same way the web app does;
   - a **"Copy results" button** (expo-clipboard or the share sheet) that exports a JSON summary: device, counters,
     bridge-delay stats, tap-test runs and the last raw messages. The owner pastes it back to us. Optionally, "Save as
     fixture" in the `src/input/fixtures/*.json` format.
6. **M8 helper (nice to have).** A Mac-side Node script `spikes/midi-probe/tools/replay-fixture.mjs` that plays a
   `src/input/fixtures/*.json` fixture to a named MIDI output (e.g. the Network MIDI session). Pick a maintained Node
   MIDI library and verify it. Unit-test the timing/loader part here; the MIDI-out part is unverified.
7. **`docs/mobile/GATE0-CHECKLIST.md`**: a printable checklist for the owner. It covers the one-time Mac/iPad setup
   (short form of the plan's §8: Xcode, Developer Mode, `npx expo run:ios --device`, trusting the profile,
   Connect-via-network, Local Network prompt), how to build and open the probe, then rows M1–M9 from the plan, each
   with exact steps, what must hold, and blanks to write the numbers in. M5 includes running the web app's latency
   test on Linux Chrome for the comparison (say exactly where it is in the web UI).
8. **`docs/mobile/GATE0.md`**: the search table, chosen versions, the design (API, clock rule, CoreMIDI choice,
   audio-clock mapping), what was verified here and how, what is **unverified** (the Swift compile, all device
   behaviour), the decision tree from the plan, and a **verdict line: "PENDING — needs the owner's device run"**,
   plus your pre-run GO / risk assessment. Also include a list of what the owner pastes back.
