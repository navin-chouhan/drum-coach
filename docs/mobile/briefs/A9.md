# Brief: A9, Test harness skeleton (Phase 1)

## Goal
Lay the test harness that Phases 2–4 grow into:
1. **T4 parity:** the score for a fixture on the iPad must equal the web score exactly. Build the reference side now.
2. **The emulated kit over Network MIDI:** a Mac-side player that replays fixtures to the iPad (M8 / T4).
3. **Maestro flow skeletons** for the simulator (T3). They can't run here; make them ready.

## Read first
`CLAUDE.md`, `docs/mobile/BOARD.md`, `docs/mobile/RECON.md` §8 (test inventory, fixtures, the Network MIDI caveat:
Wi-Fi jitter can push hits across the 15 ms crosstalk and 60 ms bounce windows), `scripts/playtest/*` (especially
`emulated-fixture.ts`), `src/input/fixtures/*.json`, `src/input/fixtures.ts`, `spikes/midi-probe/tools/*` (the M8
replayer and its timing tests, with `@julusian/midi`), `docs/mobile/GATE0-CHECKLIST.md` M8.

## Owns
`scripts/mobile-playtest/**` and `apps/mobile/e2e/**`. Nothing else. A1 is moving the engine into `packages/core` in
parallel, so **import fixtures and engine code through the current `src/` paths**. They stay valid through A1's
re-export shims. Don't import `packages/core` directly yet.

## Deliver
1. **`scripts/mobile-playtest/reference.ts`:** for each `src/input/fixtures/*.json`, run the web replay path
   (`replayFixture` from `src/input/fixtures.ts`, plus scoring as the existing fixture tests do) and write
   `scripts/mobile-playtest/reference/<fixture>.json`: hits (pad, velocity, time relative to beat 0) and the score
   summary (the same fields the run summary uses). Commit the generated references. This is the "web score" T4
   compares against.
   - **Run it with Node type stripping** (`node scripts/mobile-playtest/reference.ts`).
   - **Add a Vitest test** (`scripts/mobile-playtest/reference.test.ts`) that regenerates in memory and fails if the
     committed references drift. Root `npm test` picks it up; check it does.
2. **`scripts/mobile-playtest/replay-to-ipad.mjs`:** the Mac-side player. Start from
   `spikes/midi-probe/tools/replay-fixture.mjs` and `fixture-timing.mjs`; give it its own `package.json` here with
   `@julusian/midi`, so the root doesn't get a native MIDI dependency.
   - Options: `--list`, `--port <name>`, `--fixture <file|all>`, `--repeat n`, `--lead-ms`.
   - Print sender lateness stats.
   - Unit-test the scheduling/loader part (`node --test`). The MIDI-out part is unverified here; say so.
3. **`scripts/mobile-playtest/compare.mjs`:** takes a results JSON copied from the iPad app (format TBD in Phase 2; for
   now accept the Gate 0 probe's "Copy results" JSON and its `noteLog`) and a reference. Reports pad/velocity/timing
   differences with a tolerance flag. Run exact mode for in-app replays; tolerant mode (±5 ms, report crossings of
   the bounce and crosstalk windows) for Network MIDI. Test it with a synthetic results file.
4. **`apps/mobile/e2e/`:** Maestro flow skeletons. `launch.yaml` (app launches, the home shows "Drum Coach") and
   `dev-midi.yaml` (opens /dev/midi and sees the Devices section), plus a `README.md` with how to run them on the
   Mac simulator (`maestro test apps/mobile/e2e`). Use testIDs `home-title` and `dev-midi-devices`, and list them in
   your report so A2/A3 add them.
5. A proposal (in your report, not a root edit) for a root script `"mobile:test"` that chains `npm test` +
   `node scripts/mobile-playtest/reference.ts --check` + `cd apps/mobile && npx vitest run`.
